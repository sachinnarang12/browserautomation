1. High-Level Architecture

AutomatePortal is a three-tier web application that enables businesses to automate repetitive browser-based tasks using AI-powered browser automation (Nova Act). The system follows a classic MVC pattern with clear separation of concerns.

Key Architectural Decisions

Monolithic First

Start monolithic, evolve to microservices. A single Flask app reduces complexity for MVP while allowing future decomposition.

Server-Side Rendering

Jinja2 templates over SPA. Faster initial loads, SEO-friendly, simpler deployment. API layer can be added later for mobile/3rd-party.

Credential Isolation

Passwords stored in OS keyring, never in the database. Even a full DB compromise does not expose customer credentials.

Pluggable Automation

Nova Act is the primary engine but Selenium is available as fallback. Strategy pattern allows swapping engines per task.

2. Tech Stack Decisions

Layer Technology Version Why Chosen
Backend Python + Flask 3.9+ / 3.0+ Rapid development, rich ecosystem for automation, async-ready
ORM SQLAlchemy 2.0+ Database agnostic (SQLite → PostgreSQL/RDS migration path)
Frontend Jinja2 + Tailwind CSS 3.x / 3.x Server-side rendering, utility-first CSS, no build step needed
Automation Nova Act Latest AI-powered browser automation, handles dynamic SPAs, natural language instructions
Automation Alt Selenium 4.x Fallback engine for simpler, well-structured sites
Security Keyring + bcrypt Latest OS-level credential encryption, industry-standard password hashing
Auth Flask-Login + Flask-WTF Latest Session management, CSRF protection, remember-me support
Scheduling Schedule (Python) 1.x Lightweight, in-process job scheduling (upgradable to Celery/SQS)
Container Docker Latest Consistent environments, easy scaling, CI/CD integration
Cloud AWS (EB, RDS, CloudFormation) N/A Industry standard, auto-scaling, managed services, cost-effective at scale
Migration Path: SQLite → Amazon RDS (PostgreSQL) for production multi-tenant SaaS. The SQLAlchemy ORM abstraction makes this a configuration change, not a rewrite.

Credential Resolution Pattern

Security Pattern: Task instructions use placeholders like {{credential:5:username}} and {{credential:5:password}}. At execution time, the agent resolves these against the keyring — passwords are never stored in task definitions, logs, or the database. 
# Credential placeholder resolution flow
def _resolve_credentials(self, instructions):
    pattern = r'\{\{credential:(\d+):(\w+)\}\}'
    for match in re.finditer(pattern, instructions):
        cred_id, field = match.groups()
        credential = credential_manager.get_credential(cred_id)
        instructions = instructions.replace(
            match.group(0),
            credential[field]
        )
    return instructions

6. Docker Build

Dockerfile

# Production Dockerfile
FROM python:3.9-slim

# Set working directory
WORKDIR /app

# Install system dependencies for browser automation
RUN apt-get update && apt-get install -y \
    chromium-driver \
    libglib2.0-0 \
    libnss3 \
    && rm -rf /var/lib/apt/lists/*

# Install Python dependencies
COPY requirements_v2.txt .
RUN pip install --no-cache-dir -r requirements_v2.txt

# Copy application code
COPY . .

# Environment configuration
ENV FLASK_ENV=production
ENV PYTHONUNBUFFERED=1

# Expose port
EXPOSE 5000

# Health check
HEALTHCHECK --interval=30s --timeout=10s \
    CMD curl -f http://localhost:5000/login || exit 1

# Run application
CMD ["python", "agent_dashboard_v2.py"]

12. Lessons Learned

Architecture & Design

Start Monolithic, Split Later

Beginning with a single Flask app allowed rapid iteration. The clear module boundaries (auth, credentials, tasks, scheduler) make future microservice extraction straightforward without premature complexity.

ORM Abstraction Pays Off

SQLAlchemy's database-agnostic design means migrating from SQLite (development) to PostgreSQL (production) requires only a connection string change — no query rewrites.

Server-Side Rendering is Underrated

Jinja2 templates with Tailwind CSS deliver fast, responsive pages without a JavaScript build pipeline. For CRUD-heavy admin panels, SSR is simpler and more maintainable than a full SPA.

Credential Isolation is Non-Negotiable

Storing passwords in the OS keyring (separate from the database) provides defense-in-depth. A database breach does not expose customer credentials — this is a strong selling point for enterprise customers.

Development & Operations

V1 to V2 Migration Strategy

Building a dedicated migration tool (migrate_v1_to_v2.py) with backup, validation, and rollback proved essential. Never assume a clean migration — always provide a way back.

Browser Automation is Fragile

Websites change layouts, add CAPTCHAs, and update authentication flows. Retry logic, multi-step instruction splitting, and error recovery are essential. Nova Act's AI-based approach handles layout changes better than traditional Selenium selectors.

Environment Variables for Everything

API keys, database URLs, and secrets via environment variables (not config files) prevents accidental commits of sensitive data and enables 12-factor app deployment.

Audit Logging from Day One

Adding the AuditLog model early means every action is traceable. This is critical for enterprise customers, compliance requirements, and debugging production issues.

Security Lessons

Never Log Credentials

Credential resolution happens at the last moment before execution. Resolved values are never written to logs, database, or any persistent storage. This required careful design of the logging pipeline.

Default Passwords Must Be Changed

The default admin/admin123 account is a convenience for development. Production deployments must enforce password change on first login — this is a SaaS launch requirement.

Scaling Considerations

Scheduler Needs Isolation

Running the scheduler in the same process as the web server works for development but causes issues under load. The standalone_scheduler.py separation was a key learning — in production, use a separate ECS task or worker.

SQLite to PostgreSQL Early

SQLite's single-writer limitation becomes a bottleneck quickly with concurrent users. Plan the PostgreSQL migration before launch, not after — the SQLAlchemy ORM makes this painless.

Business & Product Lessons

Multi-Tenancy from the Start

Adding tenant_id to all models after launch is painful and risky. For SaaS, design the data model with multi-tenancy from day one, even if you only have one customer.

Usage Limits Drive Upgrades

Free/starter plan limits (5 tasks, 100 executions) naturally drive upgrades as users see value. Generous limits attract users; clear upgrade paths convert them to paid customers.

Key Takeaway: The combination of AI-powered browser automation (Nova Act), enterprise-grade security (keyring credential isolation), and a clean multi-tenant architecture positions AutomatePortal as a differentiated product in the RPA/automation market. The technical foundation supports scaling from a single user to thousands of enterprise customers with minimal architectural changes.
